## Пайплайн 1: Клиентские данные → MDM → CRM (ETL/ELT + CDC)

| Параметр | Описание |
| :--- | :--- |
| **Название** | Клиентские данные в MDM и обратно |
| **Источник** | FU CRM, RB CRM |
| **Приёмник** | MDM Customer Hub, FU CRM, RB CRM |
| **Тип** | ETL + CDC (event-driven) |
| **Инструменты** | Debezium (CDC), Kafka, Airflow, Python (дедупликация) |
| **Действия** | Read (CRM) → Validate (форматы ФИО, паспорт, ИНН) → Deduplicate (по ИНН/паспорту) → Create/Update (MDM) → Enrich (маппинг ID) → Write (CRM, обновление master_id) |
| **Частота** | Continuous (near real-time) для изменений, daily batch для сверки |
| **SLA** | < 5 минут (near real-time), < 4 часа (batch) |
| **Обоснование** | Клиенты дублируются в FU и RB. MDM создаёт золотую запись и распространяет её обратно в CRM для единого профиля. |

## Пайплайн 2: Транзакции → DWH (ELT для регламентированной отчётности)

| Параметр | Описание |
| :--- | :--- |
| **Название** | Транзакции и счета в DWH |
| **Источник** | FU Core, RB Core, FU Cards, RB Cards |
| **Приёмник** | DWH (PostgreSQL / Vertica) |
| **Тип** | ELT (CDC + Batch) |
| **Инструменты** | Debezium (CDC), Kafka, Airflow, dbt (трансформации) |
| **Действия** | Read (Core/Cards, CDC) → Load (сырые данные в staging) → Transform (dbt: агрегаты, витрины) → Validate (сверка с Core) → Write (витрины) |
| **Частота** | CDC (near real-time) для сырых данных, daily batch для витрин (ночная загрузка) |
| **SLA** | Daily batch < 4 часа (регламентированная отчётность) |
| **Обоснование** | Транзакции — основа финансовой отчётности. DWH обеспечивает строгую консистентность и воспроизводимость для регулятора. |

## Пайплайн 3: Исторические карточные операции → Data Lakehouse (Big Data)

| Параметр | Описание |
| :--- | :--- |
| **Название** | Исторические карточные операции в Lakehouse |
| **Источник** | FU Cards, RB Cards (архивные выгрузки + события) |
| **Приёмник** | Data Lakehouse (Iceberg + S3) |
| **Тип** | Streaming + Batch (CDC + архивные выгрузки) |
| **Инструменты** | Debezium (CDC), Kafka, Spark Streaming, Iceberg, Trino, Airflow |
| **Действия** | Read (CDC из Cards, 400 млн/сутки) → Enrich (добавление времени, категории) → Load (Iceberg-таблицы) → Aggregate (по датам, категориям, клиентам) → Optimize (сжатие файлов, смена партиций) |
| **Частота** | CDC (near real-time) + однократная историческая загрузка архива |
| **SLA** | < 1 минуты (latency для дашбордов), daily batch для пересчёта агрегатов |
| **Обоснование** | Карточные операции — большие объёмы (400 млн/сутки). Lakehouse дешевле хранить и быстрее сканировать. Позволяет антифроду и риску строить сложные модели без нагрузки на DWH. |

## Пайплайн 4: События клиентских каналов → Data Lakehouse (аналитика поведения)

| Параметр | Описание |
| :--- | :--- |
| **Название** | События клиентских каналов в Lakehouse |
| **Источник** | FU CRM, RB CRM, мобильное приложение (events) |
| **Приёмник** | Data Lakehouse (Iceberg + S3) |
| **Тип** | Streaming (Kafka) |
| **Инструменты** | Kafka, Spark Streaming, Iceberg, Trino |
| **Действия** | Read (события из Kafka) → Enrich (клиент, канал, сессия) → Validate (формат событий) → Load (Iceberg-таблицы) → Optimize (партиционирование по дате) |
| **Частота** | Continuous (streaming) |
| **SLA** | < 10 секунд |
| **Обоснование** | События каналов (логи, клики, обращения) полуструктурированы и объёмны. Lakehouse позволяет хранить их дёшево и анализировать для улучшения клиентского опыта и построения когорт. |

## Сценарии обработки больших исторических и событийных данных

### Сценарий 1: история карточных операций

| Поле | Значение |
| :--- | :--- |
| **Источник данных** | FU Cards, RB Cards — CDC-поток текущих операций и архивные выгрузки после слияния |
| **Характер данных** | Исторические и событийные, ~400 млн событий в сутки |
| **Целевое хранилище** | Data Lakehouse — Iceberg-таблицы на объектном хранилище (MinIO / S3) |
| **Способ обработки** | CDC (near real-time) для текущего потока + batch-загрузка исторического архива; регламентная оптимизация файлов и партиций |
| **Потребители** | Антифрод, риск-менеджмент, BI |

### Сценарий 2: события клиентских каналов

| Поле | Значение |
| :--- | :--- |
| **Источник данных** | FU CRM, RB CRM, мобильное приложение — события каналов: логи, клики, обращения |
| **Характер данных** | Событийные, полуструктурированные (JSON, Avro) |
| **Целевое хранилище** | Data Lakehouse — Iceberg-таблицы на объектном хранилище, партиционирование по дате |
| **Способ обработки** | Streaming (Kafka + Spark Streaming), SLA < 10 секунд |
| **Потребители** | BI, маркетинг, качество обслуживания |
