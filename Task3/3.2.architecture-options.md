# Сравнение архитектурных вариантов

Сравниваются три подхода к построению аналитической платформы: классический DWH на PostgreSQL,
Data Lakehouse и Data Mesh.

## 1. DWH на PostgreSQL

| Параметр | Описание |
| :--- | :--- |
| **Плюсы** | Простота развертывания, привычный SQL, ACID-гарантии, низкий порог входа для команды, хорошо подходит для регламентированной отчётности с объёмом до 10–20 ТБ. |
| **Минусы** | Ограниченное масштабирование (вертикальное), сложность с полными сканами (full scans) на больших объёмах (100+ ТБ), дорогое горизонтальное масштабирование (шардирование — нетривиально), медленные индексы на больших таблицах. |
| **Когда подходит** | Для проектов с объёмом данных до 20 ТБ, с предсказуемой нагрузкой, с регламентированной отчётностью (регуляторная, финансовая), где важна строгая консистентность и простота. |
| **Применимость к кейсу** | **Частично.** Для регламентированной отчётности (финансовой, регуляторной) DWH на PostgreSQL подходит. Но для исторических данных (400 млн+ событий в сутки) и событийных потоков PostgreSQL не справится. |

## 2. Data Lakehouse

| Параметр | Описание |
| :--- | :--- |
| **Плюсы** | Горизонтальное масштабирование (S3/MinIO + Iceberg), работа с полуструктурированными данными (JSON, Avro, Parquet), поддержка ACID через Iceberg, дешёвое хранение, возможность использовать один движок (Trino) для запросов к разным форматам, time travel и snapshot isolation. |
| **Минусы** | Сложность настройки (требуются компетенции в Trino, Iceberg, S3), более высокий порог входа для команды, требуется отдельный слой управления метаданными, латентность запросов выше, чем в реляционных СУБД для точечных операций. |
| **Когда подходит** | Для проектов с большими объёмами данных (100+ ТБ), с разнородными форматами, с историческими и событийными данными, с потребностью в time travel и воспроизводимости. |
| **Применимость к кейсу** | **Высокая.** FinUnion + RetailBank генерируют миллионы транзакций, карточных операций, событий каналов. Lakehouse идеально подходит для хранения и анализа этих данных. |

## 3. Data Mesh

| Параметр | Описание |
| :--- | :--- |
| **Плюсы** | Децентрализация владения данными (каждый домен владеет своими данными и их качеством), автономность команд, масштабирование за счёт распределённой ответственности, data-продукты как API, независимые пайплайны. |
| **Минусы** | Высокий порог входа (требуется зрелая культура данных), сложность координации между доменами, риск дублирования данных, сложность обеспечения согласованности между доменами, требует сильной платформенной команды. |
| **Когда подходит** | Для крупных организаций с несколькими бизнес-доменами (retail, SME, risk, finance), с автономными командами, с потребностью в быстрых изменениях без центрального approvals. |
| **Применимость к кейсу** | **Частично.** Финансовые и регуляторные данные требуют централизованного контроля (DWH, MDM). Однако для отдельных доменов (антифрод, маркетинг, риск) Data Mesh может быть применён как дополнение к централизованному DWH + Lakehouse. |

## 4. Выбранный подход: гибридная архитектура

**Решение: гибридная архитектура DWH + Data Lakehouse.**

**Обоснование:**

1. **DWH на PostgreSQL (или Vertica) для регламентированной отчётности.**
   Финансовая и регуляторная отчётность требует строгой консистентности, воспроизводимости и
   привычных SQL-запросов. Это «безопасная» зона, где ошибки недопустимы. DWH остаётся источником
   истины для витрин, используемых финансовым департаментом и регулятором.

2. **Data Lakehouse для исторических, событийных и полуструктурированных данных.**
   Карточные операции, логи взаимодействий, события мобильного приложения, исторические выгрузки
   из RetailBank — всё это большие объёмы данных с разнородными форматами (JSON, Avro). Lakehouse
   (Iceberg + Trino) позволяет хранить их дёшево, эффективно сканировать и агрегировать, а также
   поддерживать time travel для воспроизводимости отчётов.

3. **Разделение ответственности:**
   - **DWH:** финансовая и регуляторная отчётность, управленческая отчётность (суммы, остатки,
     агрегаты по продуктам).
   - **Lakehouse:** исторические данные для антифрода, риск-менеджмента, маркетинговой аналитики,
     поведенческих когорт.
   - **BI:** подключается к обоим источникам через единый слой витрин (Trino может делать federation).

4. **Постепенное внедрение.**
   В промежуточном состоянии (3 месяца) используется DWH на PostgreSQL + реплика для чтения.
   В целевом состоянии (12 месяцев) добавляется Data Lakehouse с миграцией больших исторических
   данных из DWH и из RetailBank.
