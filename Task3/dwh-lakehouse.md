# DWH и Data Lakehouse в архитектуре FinUnion Group

## 1. Сравнение DWH на PostgreSQL и Data Lakehouse для кейса

| Критерий | DWH на PostgreSQL | Data Lakehouse (Iceberg + Trino) |
| :--- | :--- | :--- |
| **Масштабирование** | Вертикальное; горизонтальное дорого, шардирование нетривиально | Горизонтальное за счёт S3/MinIO + Iceberg |
| **Рабочий объём** | Комфортно до 10–20 ТБ | 100+ ТБ |
| **Форматы данных** | Реляционные, структурированные | Структурированные и полуструктурированные: JSON, Avro, Parquet |
| **Транзакционность** | ACID «из коробки» | ACID через Iceberg |
| **Полные сканы больших таблиц** | Медленные, индексы на больших таблицах деградируют | Эффективны, это профильная нагрузка |
| **Точечные запросы** | Быстрые | Латентность выше, чем в реляционной СУБД |
| **Стоимость хранения** | Высокая | Низкая (объектное хранилище) |
| **Воспроизводимость отчётов** | За счёт регламентных витрин | Time travel и snapshot isolation в Iceberg |
| **Порог входа для команды** | Низкий, привычный SQL | Высокий: нужны компетенции в Trino, Iceberg, S3; отдельный слой управления метаданными |
| **Применимость к кейсу** | Частично — закрывает регламентированную отчётность, но не тянет 400 млн+ событий в сутки | Высокая — закрывает транзакции, карточные операции и события каналов FU + RB |

**Вывод для кейса.** Ни один из подходов не закрывает задачу целиком. PostgreSQL не выдерживает
объёмов карточных операций и событий клиентских каналов объединённого банка; Lakehouse избыточно
сложен и медленнее там, где нужна строгая регламентированная отчётность с точечными запросами.
Поэтому выбран гибрид.

## 2. Выбранный подход для промежуточного и финального состояния

| Горизонт | Архитектура хранения | Комментарий |
| :--- | :--- | :--- |
| **Промежуточное состояние (3 месяца)** | DWH на PostgreSQL + реплика для чтения | Быстро разворачивается, закрывает регламентированную отчётность объединённого банка на период интеграции. Lakehouse ещё не введён. |
| **Целевое состояние (12 месяцев)** | DWH (PostgreSQL) + Data Lakehouse (Iceberg + Trino) | Добавляется Lakehouse, в него мигрируют большие исторические данные из DWH и из RetailBank. DWH остаётся источником истины для отчётности. |

## 3. Роль Apache Iceberg и Trino

**Apache Iceberg — табличный формат поверх объектного хранилища (MinIO / S3):**

- даёт ACID-гарантии на данных, лежащих в объектном хранилище;
- поддерживает time travel и snapshot isolation — за счёт этого отчёт, построенный на исторических
  данных, воспроизводим на любую прошлую дату;
- позволяет управлять партиционированием (например, по дате) и эволюцией схемы;
- допускает регламентные операции обслуживания — сжатие мелких файлов, смену схемы партиционирования.

**Trino — распределённый движок SQL-запросов:**

- единый движок для запросов к данным в разных форматах (Parquet, Avro, JSON) без предварительной
  загрузки в реляционную СУБД;
- обслуживает ad-hoc аналитику финансовых аналитиков по большим историческим данным;
- за счёт federation позволяет BI обращаться к DWH и Lakehouse через единый слой витрин, не
  заставляя пользователя выбирать хранилище вручную.

## 4. Распределение данных между DWH и Lakehouse

| Хранилище | Какие данные | Почему именно там |
| :--- | :--- | :--- |
| **DWH (PostgreSQL)** | Финансовая и регуляторная отчётность; управленческая отчётность — суммы, остатки, агрегаты по продуктам; витрины для финансового департамента и регулятора | Зона, где ошибки недопустимы: нужна строгая консистентность, воспроизводимость и привычный SQL. Объёмы витрин укладываются в возможности PostgreSQL |
| **Data Lakehouse (Iceberg + Trino)** | Исторические карточные операции (400 млн+ событий в сутки); события клиентских каналов и мобильного приложения; архивные выгрузки из RetailBank после слияния; данные для антифрода, риск-менеджмента, маркетинговой аналитики и поведенческих когорт | Большие объёмы и разнородные полуструктурированные форматы (JSON, Avro). Дешёвое хранение, эффективное сканирование и агрегирование, time travel. Снимает нагрузку тяжёлой аналитики с DWH |
| **BI** | Подключается к обоим хранилищам | Единый слой витрин; federation в Trino скрывает от потребителя границу между DWH и Lakehouse |

## 5. Ограничения выбранного подхода

**Ограничения со стороны DWH на PostgreSQL:**

- вертикальное масштабирование — потолок по объёму порядка 10–20 ТБ;
- полные сканы на больших таблицах медленные, индексы деградируют;
- горизонтальное масштабирование дорого, шардирование нетривиально.

**Ограничения со стороны Lakehouse:**

- сложность настройки, нужны компетенции в Trino, Iceberg и S3 — которых у объединённой команды на
  старте нет;
- требуется отдельный слой управления метаданными;
- латентность точечных запросов выше, чем в реляционной СУБД, — Lakehouse не заменяет DWH для
  регламентированной отчётности;
- высокий порог входа для команды, что растягивает срок ввода в эксплуатацию.

_Ограничения, специфичные именно для гибрида — дублирование данных между DWH и Lakehouse, две модели
доступа и разграничения прав, стоимость federation-запросов — в текущей версии решения не раскрыты._
